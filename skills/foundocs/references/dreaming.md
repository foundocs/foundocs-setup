# Dreaming protocol

Prompt version: dreaming-v1. Read this only for an explicit Dreaming run.

## Start, inspect, and persist

1. Resolve project_id using the governing Foundocs instructions and inspect the live MCP schemas. Use dream_memory for analysis mutations and get_dream for saved status. The sole chat-approval exception is the exact archive-only workflow below. Server tool schema and responses take precedence over examples here. Do not fall back to generic content writes if a schema or capability is missing. Never call set_content_status, set_knowledge_status or move_knowledge during Dreaming; manual archival/restoration is a separate explicit-user-request workflow and must not bypass owner review.
2. Begin with `{project_id, action: "begin", requestId, agentName, promptVersion: "dreaming-v1"}`. Generate a UUID requestId for each distinct command; keep the exact payload and requestId for retries. Preserve the returned run.id, policyVersion, promptVersion, targets with versionToken, leaseGeneration, and leaseExpiresAt. The server selects eligible operations; do not broaden its policy. A duplicate-run response identifies the existing run; inspect it instead of claiming ownership or silently resuming it.
3. Page through all frozen document and knowledge targets; document-only projects are valid. The first run selects all active content; later runs cover only the server-selected new, changed, uninspected, due or related targets, including retrieval candidates. Do not claim a whole-project review. Use get_docs or get_doc with each target ID and bounded body reads; preserve versionToken and readId for continuation. Use explore_docs help for discovery grammar and get_changes for relevant history. Sources must belong to this project. Never store credentials, environment variables, or unrelated conversation transcripts as evidence. Track inspected IDs separately from targets not yet inspected. A metadata-only listing does not prove body inspection.
4. Apply the six stages below in bounded batches. Inspect related topical paths for dispersed knowledge and similar folders; prefer existing suitable folders and keep the three category roots fixed. Deduplicate findings across stages and prior runs. Use get_dream history/detail and available get_content_moves receipts to inspect previous dispositions and moves. Avoid repeated cosmetic renames or moving an item back and forth without new retrieval evidence. Do not resubmit a rejected proposal with identical evidence; a new proposal must show what materially changed. Insufficient evidence is a limited observation, not an approval task asking the owner to perform the research.
5. After each stage or bounded batch call `{project_id, action: "checkpoint", requestId, runId, leaseGeneration, stages, inspectedIds}`. Each stage result is `{stage: 3|4|5|6|7|8, status: "completed"|"not_applicable"|"deferred"|"failed", reason}`. Supply cumulative inspectedIds and stage results, including truthful zero findings, failures, and unprocessed scope. Never mark an unread target inspected. Record inspection only at its frozen version. If it changed, finish partial and explicitly resume to refresh the target inventory before inspection; repeated cumulative checkpoints do not refresh inspection times. The lease lasts 10 minutes and renews on accepted commands; checkpoint often enough to keep it current.
6. Submit self-contained candidates with `{project_id, action: "submit", requestId, runId, leaseGeneration, candidates}`. Read server outcomes; an auto_candidate request is not proof of application. Applied relations or path moves can advance endpoint versions while preserving their bodies. Re-read affected sources before submitting later candidates that share those endpoints; use the current observed versions in targets and evidence. The frozen inventory defines coverage, not an exemption from version checks. Only exact, same-scope duplicates with no metadata conflicts can receive a duplicate_of representative link; all originals remain active and unchanged. related_to links support navigation only. Same-category path-only moves follow the strict rules below. Reject self-links and cross-project links. Other relation types, rewrites, creations, category/scope/priority changes, conflict resolution, archive, and importance reduction require review; a mixed candidate with any such change requires review in full.
7. Finish with `{project_id, action: "finish", requestId, runId, leaseGeneration, status, summary}`; status is completed, partial, failed, or cancelled. Save completed for fully inspected runs, including empty/no-change runs. Use partial for budget limits, missing evidence, or unprocessed scope; explain what remains. Record deferred/failed stages in the last checkpoint. Do not wait for owner decisions to finish analysis.
8. Read `{project_id, runId}` with get_dream and report saved counts, run status, inspected/target coverage, reportUrl, and reviewUrl when pendingReviewCount is nonzero. Never infer approval, application, or task success from your intent, confidence, or a positive retrieval evaluation.

For history use get_dream `{project_id, cursor?}`; for a report use `{project_id, runId}`. Follow returned pagination. On response loss, inspect saved state and retry the identical command with its original requestId; never issue a changed retry under the same ID. On stale source versions, re-read evidence and produce a new proposal requiring review. The server rejects stale approval; never work around it with a content update or status tool.

Only an explicit user request authorizes resuming an interrupted run: `{project_id, action: "resume", requestId, runId}`. Retain the new leaseGeneration, re-read current source versions, and continue unprocessed scope. Old-generation or cancelled writes must stop; do not claim an old lease or loop on blocked commands. If the user stops, finish cancelled only while the lease still permits it; otherwise report the saved state. Persisted proposals can be reviewed by the owner after the agent exits.

## Large reports and continuation

Large responses explicitly set detailsTruncated. A receipt is not a complete inventory or proposal: do not interpret omitted evidence, mutations, or an empty inspectedIds array as absent data. run.targetTotal and run.inspectedCount remain authoritative when present. Use run.targets as one page and follow get_dream `{project_id, runId, targetOffset: run.targetNextOffset}` until targetNextOffset is null. Collect all frozen IDs and versions before claiming complete coverage. Follow top-level changeNextOffset with `{project_id, runId, changeOffset}` to inspect all change receipts; do not re-propose unseen prior changes.

To read a complete proposal, use get_dream `{project_id, runId, changeId, offset: 0, length: 8000}`. For the complete run (including full summary, stages, and inspected IDs), replace changeId with `detail: "run"`. Do not combine those selectors with targetOffset/changeOffset or history cursor/pendingOnly. Responses contain format: "json", text, offset, totalLength, nextOffset and versionToken. Concatenate text chunks in order, following nextOffset and preserving the returned versionToken on every continuation, then parse the reconstructed JSON. Offset counts Unicode code points; use the server's nextOffset, never a locally guessed byte offset. Restart at offset 0 on a version conflict. A shortened receipt's title, reason, summary, or status is not a substitute for reading the full relevant proposal before deduplication or dependency decisions.

## Stages 1–6

Use these 1-based numbers when explaining stages or reporting progress. The server retains stable API IDs for existing runs: display stages 1, 2, 3, 4, 5, 6 map to API IDs 3, 4, 5, 6, 7, 8 respectively. Use the API IDs in checkpoint `stage` and candidate `stages`; preserve IDs from saved runs.

- **1 — Memory Consolidation:** Distinguish byte-identical, same-scope duplicates from similar assertions. Assess topical placement using the folder review below, including knowledge still stored directly under a category root. Submit justified moves through the permitted Dreaming path; related links do not replace folder organization. Differences in environment, exceptions, provenance, metadata, or applicability disqualify automatic duplicate linking. A semantic merge is a reviewed rewrite; preserve every unique condition and source.
- **2 — Conflict Resolution:** Compare matching subjects, scope, environment, and time period. Distinguish historical evolution from contradiction. Cite both sources and recommend a reviewed replacement, narrower scopes, or retaining the current state. A newer date never outranks an explicit rule by itself.
- **3 — Knowledge Abstraction:** Identify recurring causes across independent experiences. Cite supporting cases, shared conditions, counterexamples, and limits. Prefer at least two independent cases; copied retellings count as one. Observations may describe patterns; activating generalized knowledge requires a reviewed create mutation.
- **4 — Forgetting & Decay:** Require concrete evidence of obsolescence, lost applicability or repeated unnecessary retrieval after current-body and counterevidence review. Age and low retrieval frequency alone do not justify archival or lower importance, especially for rules and decisions. Explain retrieval impact and reversibility. Propose recoverable archive or importance changes for review; never permanent deletion.
- **5 — Memory Linking:** Link supported shared subject matter without claiming causality or authority. Deduplicate existing relations. Only related_to and eligible duplicate_of are auto candidates. supersedes, contradicts, supports, and derived_from need review and source evidence.
- **6 — Reflection:** State documented outcome, supported explanation, useful next action, and applicability. Positive retrieval feedback measures retrieval usefulness, not task success. One incident can support a bounded lesson, never an unsupported universal rule.

## Archive review and retrieval evidence

Use `get_archive_candidates` with `{project_id, runId}` from this run, then follow list `nextCursor` with the same filters. Candidates come only from the frozen targets. The window is the 168 hours ending at run start; at least four latest not_beneficial evaluations on distinct logical reads make a review candidate. Retries, chunks and multiple versions of the same key/readId/content count once. These counts never authorize automatic archival. A limit is an upper bound: UTF-8 response budgets can return fewer items or evidence records. Do not assume a fixed page size.

For every relevant candidate, read all `retrievals` by continuing with `{project_id, runId, contentId, evidenceOffset: nextEvidenceOffset, evidenceVersion}` until nextEvidenceOffset is null. Continue the list separately with nextCursor. On VERSION_CONFLICT after an evaluation correction, content edit, archival, deletion or leaving the candidate set, discard the old evidence snapshot and restart the candidate/evidence read from the beginning. Do not splice evidenceVersion snapshots together.

Read the current complete body with get_doc/get_docs at the returned versionToken. Compare counts.currentVersionNotBeneficial and counts.olderVersionNotBeneficial, actual evaluation reasons, purpose/task context, and beneficial records. An old problem already fixed in the current body is not a reason to propose again. Still-valid content can merit review for repeated unnecessary retrieval, but explain its useful applications and counterevidence. Four negative ratings do not cancel beneficial uses. Direct evidence of a retired feature, ended experiment or replaced policy can justify a proposal without retrieval counts; cite the relevant replacement or decision. Age and non-use alone never justify archive or importance reduction. Do not re-propose a rejected finding with the same evidence under a new title or explanation.

Submit archive-only `review_candidate` proposals with `{type: "archive", contentId}`, current targets/versionTokens and contiguous current-body excerpts in evidence. Keep retrieval statistics separate: `retrievalEvidence: [{contentId, versionToken, retrievalId, evaluationId, currentContentReason}]` references actual delivered retrieval/evaluation IDs and explains why that evaluated problem still applies to the current content. Never invent IDs or put an evaluation paraphrase into body evidence. The server verifies references and saves a fixed archiveReview snapshot, including beneficial counterevidence and the impact of exclusion from default retrieval. Explain the target, reason, counts and reasons or direct invalidation evidence, useful uses, and reversible retrieval impact for the human. Documents allow archive only; knowledge's other reviewed operations do not extend to documents.

## Specific human chat approval

Archive proposals always remain for review until the human approves in the UI or explicitly approves that specific proposal in the current chat. A general Dreaming request, scheduled execution, old/quoted/stored conversation, ambiguous agreement, or model confidence is not approval. Do not explore past conversations or add recurring execution to obtain it. Analysis can finish while review is pending.

After that explicit approval, read the exact saved archive-only proposal with get_dream, including full detail/continuations and current revision/hash, then call `approve_archive_proposal` with `{project_id, runId, changeId, revision, hash, requestId, approval: {source: "human_chat", text: <short explicit approval sentence>}}`. Send only the approval sentence (at most 500 characters), never the full conversation. The key relays the human instruction; decisionActor records the actual AI key, not a verified human session. Other mutations or unresolved dependencies cannot be approved by this tool. Never use generic writes or either status tool to apply a Dreaming proposal. If unavailable, link the UI review instead.

Reuse the exact input/requestId after response loss; reconcile a stale revision, hash, body or retrieval snapshot by rereading and obtaining approval for the current specific proposal, never silently applying changed content. Read get_dream to confirm the saved applied status. UI approve/reject/defer/revert shares this state; preserve its conflict and undo rules. This exception does not authorize agent approval or reversion of other Dreaming changes.

## Folder organization review

For inspected targets, compare plausible same-category topic groups with their current placement and nearby existing folders. Keep the run's selected scope: listing nearby paths does not make their bodies inspected or authorize mutations outside the frozen targets.

- Group by shared subject and applicability, using the inspected content as evidence. Reuse a suitable existing folder, or choose a coherent topic folder when it makes related knowledge easier to find together. A folder does not need to exist already to be useful.
- For each plausible group, record the affected paths, proposed destination and retrieval benefit in its candidate or consolidation checkpoint reason. If retaining the paths, explain the specific scope mismatch, mixed topic or other reason that makes the group unhelpful. Clear filenames and valid root-level storage alone are insufficient reasons to skip this comparison.
- When a move is justified, submit it using the server-permitted disposition below. Do not stop at mentioning a possible folder or substitute only a related_to link. Preserve independent scopes and avoid one-file folders, cosmetic renames and repeated moves without a retrieval benefit.
- Zero moves remain valid when the comparison supports retaining the current placement. Report that conclusion and its concrete basis; do not create folders or proposals just to fill a quota. If the assessment remains unprocessed, defer the stage and report the remaining scope rather than marking it completed.

## Folder moves and undo

Knowledge has fixed `knowledge/rules/`, `knowledge/learnings/` and `knowledge/decisions/` roots, with arbitrary topical nesting below them. Use the existing six stages for folder findings; do not add another stage or create empty folder records. Inspect live dream_memory policy before requesting an automatic move. If the connected server does not explicitly support server-verified same-category path-only updates, submit a review candidate instead. Tool presence or a client-side claim that a move is harmless is insufficient. Do not retry a missing capability with generic content writes.

A path-only move uses `{type: "update", contentId, after: ContentInput}`. Copy the complete inspected content into `after` with only `path` changed, and supply the change `reason`. Keep `kind: "knowledge"`, category, title, TL;DR, the exact body bytes, ordered tags, immutable creation date and all other content metadata unchanged. Do not include server-owned fields such as linkBasePath, memoryStatus or importance in ContentInput. The server compares stored fields independently; any semantic or category change, or a candidate mixed with archive, importance, creation or other reviewed mutations, requires owner review in full. Keep independent decisions separate without splitting an inseparable semantic change to evade review. Automatic eligibility is always server-controlled.

Moves preserve the stable content ID, previous-path aliases, history and relative Markdown link base through the server's linkBasePath. Never recreate/delete a memory, rewrite its body to adjust links, or manually set server-owned fields for folder organization. A path collision or stale version is not permission to overwrite. Re-read affected items after application and use saved outcomes to report moved paths; do not infer success from submission.

Use get_content_moves when available for move receipts, including dreamRunId and changeId, and get_dream for the exact saved proposal. Reverting a Dreaming move requires the owner review's existing `revert` action on that proposal and its current revision/hash; the agent never approves or reverts move proposals itself. Link the exact proposal review when available. Do not use undo_content_move, update_doc or a new compensating proposal to bypass that review. Ordinary non-Dreaming move undo is a separate explicit-user-request workflow in [the writing guide](../../foundocs-capture-knowledge/references/writing-guide.md#authorized-path-moves-outside-dreaming).

## Candidate payload

A candidate contains candidateId (a fresh UUID), stages, title, reason, impact, targets, evidence, mutations, dependsOn, alternatives, uncertainty, and requestedDisposition. The submission envelope supplies runId; do not add operation or before/after fields from obsolete planning examples. targets is an array of `{contentId, versionToken}` for the frozen documents or knowledge involved. Documents allow archive mutations only, never update/create/importance/relations. evidence is an array of `{contentId, versionToken, location, excerpt}`. Copy each excerpt as a contiguous verbatim passage from the inspected source body at that version. Do not translate, paraphrase, summarize relations, or invent text in excerpt, even when the interpretation is correct; put those interpretations in reason or impact instead. Documents may also provide current body evidence for their archive proposals; external-to-target content is evidence only. Use the current live schema for ContentInput.

mutations accepts:

- `{type: "relation", fromId, toId, relation: "duplicate_of"|"related_to"|"supersedes"|"contradicts"|"supports"|"derived_from"}`
- `{type: "archive", contentId}`
- `{type: "importance", contentId, importance: "normal"|"low"}`
- `{type: "update", contentId, after: ContentInput}`
- `{type: "create", after: ContentInput}`

requestedDisposition is auto_candidate, review_candidate, or observation. An observation has no mutations. A creation's after includes complete proposed knowledge and path. Bundle inseparable changes in one candidate; keep independent decisions separate. dependsOn names prerequisite saved change IDs, as required by the live schema; do not guess them. Alternatives and uncertainty are arrays of concise statements. Reasons summarize evidence rather than revealing private reasoning. The server stores before/after snapshots, IDs, revisions, hashes, eligibility and final status. Fully specify the executable change so review never requires the original agent session.

## Final response

Use the user's language. State the project, saved run status, automatically applied count, review pending count, observations, and inspected/target coverage. Link the saved report and, when applicable, owner review. Mention the most consequential supported finding briefly. For partial runs state the interruption and remaining scope; for zero justified changes say so plainly. Never inflate proposals to fill a stage or call analysis pending just because owner decisions remain.
