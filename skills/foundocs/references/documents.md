# Documents and knowledge

- Save user-requested documents in this project's Foundocs documents by default. Save durable user-provided project context, lasting rules and preferences, confirmed decisions and verified reusable learnings in Foundocs knowledge.
- Knowledge stays under the fixed `knowledge/rules/`, `knowledge/learnings/` and `knowledge/decisions/` roots. Reuse related topical folders, nesting when useful; files directly under a category root remain valid. Group related items and avoid duplicate shallow folders. Folder organization never changes an item's meaning or category implicitly.
- Explicit user destinations and formats take precedence. Keep specifications under the repository's existing spec conventions.
- After resolving the configured project, on its first Foundocs use in each session call `get_project_context` with `project_id` and `view: "index"` once, if the live schema supports it. Reuse an index already read, and read a new one when switching projects. This is guidance, not a guaranteed session-start hook. If an older server lacks index mode, use the existing context call without `view` and continue searching; authentication and project errors still require correction.
- The bounded index lists titles, TL;DRs and paths selected from frequently retrieved, recently beneficial and recently updated items. It is only a starting point: missing entries do not prove absence. If it has no relevant item or information is insufficient, continue with `search_docs` and `explore_docs` across all active content before deciding nothing exists or creating a new topic. Index exposure does not count as retrieval.
- When project context is needed, prefer `explore_docs` for path/body exploration and focused reads; use `search_docs` for title, tag or TL;DR searches. Read only related documents or ranges. Reuse information already read unless it changed or needs checking. For several known exact targets, use `get_docs`; inspect every item result and follow its per-item nextOffset/versionToken with the same ordered targets and readId. Authorized same-category directory moves can use `move_knowledge` with observed versions; the entire batch rolls back on conflicts. See the main skill for batch limits and older-server fallback.
- When the user explicitly provides durable project information (purpose, identity, target users, technical foundation, terminology, operating environment, constraints, preferences or confirmed direction), use [foundocs-capture-knowledge](../../foundocs-capture-knowledge/SKILL.md) in the same turn even without a request to remember or save. Also use it for confirmed decisions, lasting rules and verified reusable findings.
- Accept explicit project statements as user-provided context without requiring code verification; record that source and do not infer unstated reasons or details. Classify basic project context as `learnings`, confirmed choices as `decisions`, and lasting behavioral instructions and preferences as `rules`.
- Search narrowly for related knowledge, merge into the same topic or create an item, and confirm success before reporting a save. Acknowledgment alone is insufficient. If saving is blocked, report that it was not saved and why. Before the final response, check only for omissions in the current context.
- Do not automatically save questions, hypotheses, ideas under consideration, one-off requests, temporary progress or secrets. Skip equivalent existing knowledge. When claims conflict, apply an explicit user correction; otherwise clarify before replacing the disputed claim.
- If there is no new knowledge worth saving, skip skill loading, collection calls, writes and collection reports. Do not retrieve entire conversations, load all documents or invoke additional models or subagents solely for collection.
- Foundocs manages its indexes and change history. Do not duplicate them in local INDEX files or JSONL logs.
