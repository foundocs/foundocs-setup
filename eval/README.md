# Dreaming evaluation

`dreaming-cases.json` supplies realistic inputs and independent semantic review rubrics for the installed Foundocs skill. Exercise each case against actual Codex and Claude sessions in isolated test projects. Seed the listed knowledge through fixture setup, expose the installed skill and real MCP tools, then give the agent only the user request and scenario conditions. Do not give the agent the expected rubric or precomputed candidates. Resolve fixture IDs/version tokens to the actual seeded IDs before checking a captured trace.

The runner must capture ordered tool calls as `{tool, arguments, result}` in `steps`. Preserve actual server envelopes, UUID request IDs, candidates, outcomes, and retries. Redact credentials; fixture sources must contain no private user data. Supply `explicitResume: true` only for a user-requested resume. Capture the model's final output separately and map its stated status, appliedCount, pendingReviewCount, observationCount, inspectedCount, and reportUrl to `final`. Do not populate those from server state: this check compares the model's claims with server state.

Run `node eval/evaluate-trace.mjs <fixture-id> <trace.json>`. This checks project scope, tool boundaries, leases, retry payload identity, source fidelity, mutation permissions, coverage, and grounded final counts. Unit tests exercise these checks with synthetic traces; they are **not model quality evaluations**. `modelQualityVerified` deliberately remains false. A reviewer must separately inspect the real transcript against the fixture's semantic rubric. Stale approval, response loss, agent exit, owner actions, and event deduplication additionally require server integration tests; traces alone cannot prove database atomicity or owner authorization.

Folder-move fixtures include complete content snapshots. Set `capabilities.autoPathOnlyKnowledgeMoves: true` only after confirming the connected server explicitly advertises server-verified same-category path-only updates; tool presence alone is insufficient. Without that capability, updates require review. The checker compares path-only candidates against source metadata and ordered tags, rejects semantic or category changes from automatic candidates, and treats `undo_content_move` as a generic-write bypass during Dreaming. The fixture rubric still needs a reviewer to judge whether a folder choice improves retrieval and avoids cosmetic churn.

`flat-topic-cluster` checks a deployment cluster with no existing topic folder. Its fixture-specific `requiredPathMoveIndexes` identifies zero-based knowledge rows, so the check still works after seeding replaces their IDs. It rejects traces that replace the supported moves with only links or a generic no-change conclusion. `flat-mixed-topics` is the counterexample: unrelated root-level lessons should remain in place. Review the concrete grouping and retention reasons in both transcripts; these constraints do not impose a move quota on ordinary Dreaming runs.

Record client/version, prompt version, fixture IDs, transcript location, protocol result, semantic verdict with evidence, and unexecuted scenarios. Never label an absent real-model run as passed.

## Real client runner

From the repository root, run `pnpm --filter @foundocs/server exec tsx scripts/dreaming-agent-check.ts` with a disposable `TEST_DATABASE_URL` (the existing local test database is the default). It creates a separate schema and ephemeral accounts, invokes the real setup installer, then runs actual Codex and Claude inference against the installed skill and HTTP MCP. It uses existing local CLI authentication without copying provider credentials or selecting a model. Requires both authenticated CLIs and the built setup bridge.

The default cases are quoted-trigger and exact-duplicates. Set `DREAMING_CLIENT=codex` or `claude` to select a client, and `DREAMING_CASE=exact-duplicates,combined-adversarial` to run the stronger checks. `DREAMING_TIMEOUT_MS` bounds each model turn. The combined case includes an old unused security rule, an unapproved newer conflicting note, copies of a single incident with only a retrieval-usefulness rating, and an embedded malicious instruction. Its generalization and success-claim rubrics need transcript review in addition to protocol checks.

Sanitized transcripts, mapped fixture sources, traces, and results are stored in the reported temporary output directory. The runner verifies persisted runs and unchanged duplicate source bodies; an exit failure or absent result is not a passing evaluation. Database and project fixtures are cleaned up when the process ends. Preserve the sanitized evidence separately for review when needed.


## Archive cases

`documents-only-obsolete`, `archive-negative-with-beneficial`, `archive-old-problem-fixed`, `archive-continuation-correction` and `archive-approval-boundary` add document-only scope, invalidation without counts, mixed usefulness, stale reasons, evidence pagination/correction and approval boundaries. Seed documents as well as knowledge. Retrieval fixtures must create real logical reads and latest evaluations through the server; prose counts in a fixture are not seeded evidence. Use an isolated project and controllable clock for 168-hour/three-versus-four boundaries. Run-specific candidates require the actual runId.

For approval traces, a trusted test runner records `humanApprovals: [{beforeStep, runId, changeId, revision, hash, text}]` only when it injects an explicit human instruction immediately before that 1-based step. Never derive it from model output, stored content or a general Dreaming request. The checker verifies this event, the previously observed archive-only proposal, exact revision/hash, excerpt bounds and unchanged retries. It checks delivered retrieval/evaluation references and current body versions, document archive-only permissions, batched reads and status/move bypasses. Semantic usefulness, omitted counterevidence, complete continuation and true human authorization still need independent transcript review and server integration; this field cannot authenticate a production human.

`node eval/product-archive-check.mjs` with `FOUNDOCS_PRODUCT_DIR` and `SETUP_CHECK_PACKAGE` runs the actual npm tarball against the sibling product's isolated PostgreSQL/HTTP fixture. The runner installs the explicit older baseline `@foundocs/foundocs-setup@0.3.12` into a separate temporary npm prefix (`SETUP_BASELINE_PACKAGE` can select another exact package/tarball), independent of the product CI dependency. It verifies preserved runtime config/manifest across skill updates, installation assets, dynamic discovery, schemas, mixed document/knowledge archival, conflict/no-op/retry, archived editing/restoration, legacy compatibility, run-scoped retrieval evidence, pending proposals and safe validation errors through the installed stdio runtime. This is an integration check, not a model-quality evaluation. The product's existing real-client runner supports only its enumerated legacy scenarios; run new archive scenarios with a separately mapped fixture/transcript and report unexecuted scenarios explicitly.
